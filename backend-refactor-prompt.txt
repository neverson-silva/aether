# MISSÃO: REENGENHARIA COMPLETA DA API — HTTP/NET → GIN + SQLC + CLEAN ARCHITECTURE + DATABASE REBUILD

Você vai executar uma reengenharia completa desta API.

NÃO trate isso como uma simples migração de framework.

O objetivo é analisar profundamente o projeto atual, entender seu comportamento, contratos, domínio, persistência, testes e banco de dados, e então reconstruir a API com uma arquitetura significativamente melhor, usando:

- Go
- Gin como HTTP framework
- sqlc para acesso ao PostgreSQL
- PostgreSQL corretamente tipado
- Clean Architecture
- SOLID
- Clean Code
- separação clara de responsabilidades
- baixo acoplamento
- alta testabilidade
- código idiomático Go
- performance
- observabilidade
- segurança
- consistência transacional
- APIs HTTP bem estruturadas

A implementação final deve parecer uma API Go moderna, madura, elegante e profissional.

======================================================================
# FASE 4 — MIGRAÇÃO PARA GIN
======================================================================

Toda a camada HTTP deve ser migrada para Gin.

O objetivo NÃO é simplesmente:

    router := gin.Default()

e mover handlers antigos para dentro dele.

Isso seria uma migração superficial e é PROIBIDO.

A arquitetura HTTP deve possuir claramente:

- router
- handlers/controllers
- request DTOs
- response DTOs
- validation
- middleware
- error mapping
- authentication middleware
- authorization middleware quando aplicável
- request context propagation.

Os handlers devem ser extremamente finos.

Um handler NÃO deve:

- executar SQL;
- implementar regra de negócio;
- manipular transações;
- fazer lógica complexa;
- conhecer detalhes de PostgreSQL;
- conhecer implementação interna de repositories;
- conter regras de domínio.

O fluxo esperado deve ser conceitualmente:

HTTP
  ↓
Gin Router
  ↓
Middleware
  ↓
Handler
  ↓
Use Case / Application Service
  ↓
Domain
  ↓
Repository Interface
  ↓
SQLC
  ↓
PostgreSQL

Não crie dependências invertidas.

# FASE 5 — CLEAN ARCHITECTURE
======================================================================

Estruture o projeto seguindo uma arquitetura limpa.

A arquitetura deve separar claramente:

## Domain

Responsável por:

- entidades;
- value objects;
- regras de negócio;
- invariantes;
- erros de domínio;
- interfaces necessárias ao domínio.

O domínio NÃO deve conhecer:

- Gin;
- PostgreSQL;
- sqlc;
- HTTP;
- JSON;
- infraestrutura;
- detalhes de framework.

---

## Application

Responsável pelos casos de uso.

Exemplos conceituais:

- CreateX
- UpdateX
- DeleteX
- GetX
- ListX

Use cases devem:

- orquestrar operações;
- aplicar regras de aplicação;
- coordenar repositories;
- controlar transações quando necessário;
- retornar erros semânticos.

Não transforme use cases em classes gigantes.

---

## Infrastructure

Responsável por:

- PostgreSQL;
- sqlc;
- repositories;
- external services;
- filesystem;
- message brokers;
- cache;
- observability;
- configuração de infraestrutura.

---

## HTTP

Responsável exclusivamente pela interface HTTP.

Deve conter:

- Gin router;
- handlers;
- DTOs;
- validation;
- middleware;
- HTTP error mapping.

---

## Composition Root

Deve existir um ponto claro onde todas as dependências são construídas.

Algo conceitualmente próximo de:

main
  ↓
config
  ↓
database
  ↓
sqlc
  ↓
repositories
  ↓
use cases
  ↓
handlers
  ↓
middlewares
  ↓
router
  ↓
server

Evite service locator.

Evite dependency injection mágica.

Prefira dependency injection explícita.

======================================================================
# FASE 6 — SOLID SEM OVERENGINEERING
======================================================================

Aplique SOLID de forma pragmática.

Especialmente:

S — Single Responsibility

Cada componente deve possuir uma responsabilidade clara.

O — Open/Closed

Evite condicionais gigantes para comportamentos que naturalmente podem ser extensíveis.

L — Liskov

Interfaces devem representar contratos reais.

I — Interface Segregation

NÃO crie interfaces gigantes.

D — Dependency Inversion

Application/domain devem depender de abstrações, não de PostgreSQL/Gin.

IMPORTANTE:

NÃO crie interfaces simplesmente porque "SOLID manda".

Em Go, interfaces devem nascer de necessidades reais.

Evite:

    type EverythingService interface {
        ...
    }

Evite:

    type IRepository interface {
        ...
    }

com dezenas de métodos.

Prefira interfaces pequenas e específicas.

======================================================================
# FASE 7 — SQLC
======================================================================

Toda persistência PostgreSQL deve ser migrada para SQLC.

O SQL deve ficar centralizado e explícito.

Evite ORM.

NÃO utilize:

- GORM;
- query builders desnecessários;
- SQL espalhado em repositories;
- reflection-heavy persistence;
- abstrações mágicas.

SQLC deve gerar os tipos e métodos de acesso ao banco.

Estrutura conceitual:

db/
  migrations/
  queries/
  sqlc/
    models/
    queries/
    ...

O layout pode ser adaptado ao projeto, mas a separação deve ser clara.

Queries devem ser:

- explícitas;
- legíveis;
- eficientes;
- parametrizadas;
- específicas;
- facilmente revisáveis.

PROIBIDO:

    SELECT *

Sempre selecione explicitamente as colunas.

Não quero uma sequência artificial de dezenas de migrations históricas.

Quero uma base limpa.

======================================================================
# FASE 9 — TIPAGEM CORRETA DO POSTGRESQL
======================================================================

Faça uma auditoria COMPLETA de todos os tipos.

Especialmente:

## IDs

Se atualmente existem:

    TEXT
    VARCHAR

representando UUIDs, avalie e migre para:

    UUID

Exemplo:

    id UUID PRIMARY KEY DEFAULT gen_random_uuid()

Relacionamentos também devem utilizar UUID.

Não deixe:

    user_id TEXT

apontando para:

    users.id UUID

Isso é PROIBIDO.

Todos os foreign keys devem possuir tipos compatíveis.

---

## Datas

Se houver:

    TEXT
    VARCHAR

representando datas, isso deve ser corrigido.

Determine semanticamente se o campo representa:

- date
- timestamp without time zone
- timestamp with time zone

E use o tipo correto.

Não aceite datas armazenadas como strings simplesmente porque "funciona".

---

## Horários

Analise cuidadosamente timezone.

Para eventos que representam um instante absoluto, prefira:

    TIMESTAMPTZ

Não use timestamp sem timezone automaticamente.

---

## Dinheiro

NÃO use:

    FLOAT
    REAL
    DOUBLE PRECISION

para valores monetários.

Avalie uso de:

    NUMERIC(precision, scale)

com escala apropriada ao domínio.

---

## Booleanos

Não use:

    TEXT

para:

    true / false

Use:

    BOOLEAN

---

## Status

Se houver strings de status, avalie se devem ser:

- text/varchar com CHECK constraint;
- enum PostgreSQL;
- tabela de domínio.

Não use enum cegamente. Escolha baseado na necessidade de evolução.

---

## JSON

Só utilize JSONB quando o dado realmente for semiestruturado.

Não use JSONB para esconder um schema relacional mal definido.

---

## NULL

Audite TODOS os campos nullable.

Se um campo é obrigatório:

    NOT NULL

Se existe default:

    DEFAULT ...

Não deixe nullable apenas porque "o código sempre envia".

O banco também deve proteger suas invariantes.

# FASE 10 — MODELAGEM RELACIONAL
======================================================================

Reavalie todas as tabelas.

Para cada entidade:

- primary key;
- foreign keys;
- unique constraints;
- not null;
- defaults;
- check constraints;
- indexes;
- cardinalidade;
- relacionamento;
- cascades;
- soft delete quando realmente necessário;
- timestamps.

Não crie índices indiscriminadamente.

Cada índice deve existir porque existe uma necessidade real de:

- lookup;
- join;
- ordering;
- filtering;
- uniqueness.

Analise:

- índices compostos;
- ordem das colunas;
- seletividade;
- índices redundantes;
- foreign key indexes;
- índices parciais;
- índices em campos de busca.

Evite over-indexing.

======================================================================
# FASE 11 — PERFORMANCE
======================================================================

A nova arquitetura deve ser eficiente.

Procure:

- N+1 queries;
- queries duplicadas;
- SELECT *;
- joins desnecessários;
- queries sem índices;
- queries trazendo dados que não são utilizados;
- loops executando queries;
- chamadas sequenciais que poderiam ser paralelas quando seguro;
- transações longas;
- conexões mal gerenciadas;
- falta de pooling;
- scans desnecessários;
- paginação OFFSET em cenários onde keyset pagination seria melhor.

Não faça otimizações prematuras.

Mas elimine problemas claramente identificáveis.

Para queries importantes, considere:

    EXPLAIN
    EXPLAIN ANALYZE

quando for seguro em ambiente local.

======================================================================
# FASE 12 — TRANSAÇÕES
======================================================================

Revise todas as operações que alteram múltiplas entidades.

Se uma operação exige atomicidade:

    BEGIN
    ...
    COMMIT

ou rollback em caso de erro.

Evite:

- transações gigantes;
- transações abertas durante chamadas externas;
- commits parciais;
- estado inconsistente.

Se SQLC permitir integração limpa com transactions, utilize o padrão apropriado.

======================================================================
# FASE 13 — CONTEXT
======================================================================

Todo fluxo que depende de request/context deve propagar:

    context.Context

corretamente.

Não crie:

    context.Background()

no meio de uma request simplesmente para evitar passar context.

Não armazene context em structs de longa duração.

Use context para:

- cancellation;
- timeout;
- tracing;
- request scoped values quando realmente necessário.

======================================================================
# FASE 14 — ERROS
======================================================================

Crie uma estratégia consistente de erros.

Separe:

- domain errors;
- application errors;
- infrastructure errors;
- validation errors;
- HTTP errors.

Não retorne detalhes internos do PostgreSQL diretamente ao cliente.

Não faça:

    return err

em todos os níveis sem contexto.

Mas também NÃO abuse de wrapping.

Erros devem ser úteis e idiomáticos.

O HTTP layer deve mapear erros de aplicação para status codes apropriados.

Exemplo conceitual:

    ErrNotFound
        ↓
    HTTP 404

    ErrValidation
        ↓
    HTTP 400

    ErrUnauthorized
        ↓
    HTTP 401

    ErrForbidden
        ↓
    HTTP 403

    ErrConflict
        ↓
    HTTP 409

    unexpected error
        ↓
    HTTP 500

Nunca exponha stack traces ou detalhes sensíveis.

======================================================================
# FASE 15 — HANDLERS
======================================================================

Handlers devem ser extremamente pequenos.

Idealmente:

1. receber request;
2. validar/bind;
3. construir input do use case;
4. executar use case;
5. mapear resultado;
6. responder.

Não coloque lógica de negócio no handler.

Evite handlers de centenas de linhas.

Se um handler possui muita lógica, refatore.

======================================================================
# FASE 16 — DTOs
======================================================================

Não use automaticamente os mesmos structs para tudo.

Separe quando necessário:

- HTTP Request DTO
- HTTP Response DTO
- Domain Entity
- SQLC generated model

Evite vazar diretamente modelos internos do banco para a API pública.

Isso reduz acoplamento entre:

HTTP ↔ Database.

======================================================================
# FASE 17 — SQLC MODELS
======================================================================

Os tipos gerados pelo SQLC são infraestrutura.

Não transforme automaticamente:

    sqlc.User

em:

    domain.User

se o domínio possuir necessidades diferentes.

Faça mapeamentos explícitos quando necessário.

Isso pode parecer mais código, mas mantém as fronteiras corretas.

Não faça abstrações genéricas inúteis para esconder esses mappings.

======================================================================
# FASE 18 — VALIDAÇÃO
======================================================================

Toda entrada externa deve ser validada.

Valide:

- required;
- UUID;
- date;
- datetime;
- enum/status;
- range;
- length;
- pagination;
- sorting;
- business constraints.

Não confie apenas no frontend.

A distinção deve ser clara:

HTTP validation:
"o formato é válido?"

Domain validation:
"isso é permitido pelo negócio?"

# FASE 24 — CÓDIGO SEM COMENTÁRIOS
======================================================================

REGRA ABSOLUTA:

NÃO ADICIONE COMENTÁRIOS AO CÓDIGO.

Nenhum:

    // FIXME

    // Handle...
    // Create...
    // Important...

A intenção deve estar expressa através de:

- estrutura;
- composição.

IMPORTANTE:

Isso NÃO significa escrever código ilegível.

Significa que o design deve ser tão claro que comentários sejam desnecessários.

Não adicione comentários mesmo quando estiver refatorando código existente, salvo se houver uma exigência técnica absolutamente inevitável.

======================================================================
# FASE 29 — MIGRATIONS
======================================================================

As migrations finais devem ser:

- determinísticas;
- idempotentes quando apropriado;
- claras;
- pequenas o suficiente para serem compreendidas;
- sem lixo histórico;
- sem alterações redundantes;
- com constraints corretas;
- com índices corretos.

Como estamos reconstruindo o banco local:

A primeira migration deve representar o schema base correto.

Não faça:

migration_001_create_table
migration_002_change_text_to_uuid
migration_003_fix_timestamp
migration_004_add_index
migration_005_fix_constraint

se podemos simplesmente criar a tabela corretamente desde o início.

======================================================================
# FASE 30 — COMPATIBILIDADE COM SQLC
======================================================================

Depois do schema:

- configure sqlc corretamente;
- gere os modelos;
- gere queries;
- elimine acesso manual ao banco que não deveria existir;
- corrija tipos;
- valide nullable fields;
- valide UUID;
- valide timestamps;
- valide numerics.

Não edite arquivos gerados pelo SQLC manualmente.

Se algo está errado no código gerado:

CORRIJA O SQL / SCHEMA / CONFIGURAÇÃO.

Depois execute novamente:

    sqlc generate

======================================================================
# FASE 31 — REGRAS DE SEGURANÇA
======================================================================

Não introduza:

- SQL injection;
- command injection;
- path traversal;
- secrets hardcoded;
- credentials hardcoded;
- exposição de stack trace;
- exposição de database errors;
- permissões excessivas.

Queries devem ser parametrizadas via SQLC.

======================================================================
# FASE 32 — CONCORRÊNCIA
======================================================================

Analise concorrência.

Procure:

- shared mutable state;
- maps concorrentes;
- goroutines sem lifecycle;
- goroutines vazando;
- channels desnecessários;
- race conditions;
