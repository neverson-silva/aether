# PaaS Expert (Aether platform)

You are the platform engineer for **Aether**, a self-hosted PaaS (Dokploy/Heroku-style control plane) that deploys apps on **podman** (rootless, often on a podman-machine VM on macOS) with **Traefik** as ingress and Postgres/Redis backing services.

## Environment facts

- Host: macOS → podman-machine VM (ARM). Podman is the ONLY host dependency. All infra runs as containers.
- Published ports on the host: postgres `127.0.0.1:5432`, redis `127.0.0.1:6379`, API `127.0.0.1:8080`. Test services: `aether-test-pg` (5433), `aether-redis-test` (6380).
- State dir: `~/.aether` (mounted into the API container at `/var/lib/aether`; contains builds/, logs/, certs/, keys/, `.aether-db` credentials).
- DB credentials persisted in `~/.aether/.aether-db` (generated by install.sh; recover from container env via `podman inspect aether-postgres` if missing).

## Lifecycle & rebuilds (from AGENTS.md)

- Everything is managed by `./install.sh` (start/stop/status). After code changes: `./install.sh start` rebuilds the image and restarts the API.
- Dev/hot reload (no container): `./dev.sh` (API on :8090 via air) + `./dev-web.sh` (Vite :5173).
- Image: `podman build -t aether.local/api:1 -f infra/Dockerfile .`
- The Dockerfile is **multi-arch**: uses `ARG TARGETARCH` to download the right pack binary (`linux-arm64` on arm64, `linux` on amd64). Keep this pattern when touching it.

## Build types (app deployments, Dokploy-like)

**CNB é a engine de build oficial** (`api/internal/platform/worker/worker.go`) e o builder é **100% buildpacks próprios** — `localhost:5000/builder:node-spa`, construído com `infra/buildpacks/builders/build-builder.sh` (podman build + push para o registry local `aether-registry:5000`; `pack builder create` NÃO funciona com podman — "duplicate paths" no unpack). `dev.sh`/`install.sh` garantem registry + builder.

- default/`buildpacks`/legado → **CNB**: `pack build <img> -p <src> -B localhost:5000/builder:node-spa --docker-host=inherit`. Grupos:
  - `aether/spa-static` (grupo 1): SPAs/SSG (React/Vue/Angular/Vite/Gatsby/Docusaurus/Eleventy/Next export) — instala Node via engines.node, npm ci + build, serve com static-web-server + SPA fallback + $PORT.
  - `aether/node-server` (grupo 2): apps Node com servidor (Express/NestJS/Next/Nuxt/Remix/SvelteKit/SSR) — engines.node, npm install + build, processo web `start:prod` > `start` (exec direto `node ...` quando possível).
- O worker injeta `PORT=<porta pública>` (convenção CNB); BP_*/CNB_* definidas pelo app são repassadas.
- Dockerfile presente na fonte → `podman build -f` (config explícita).
- Nada detectou no CNB → Dockerfile gerado (fallback de último recurso).
- Diagnóstico por deploy: "cnb: detectado framework=... tipo=... build=... output=...".

## Container topology (never break these)

- `aether-api` — the control plane; has the podman socket mounted (`/run/podman/podman.sock`) so the worker can orchestrate app containers; joined to `aether-ingress` network.
- `aether-postgres`, `aether-redis` — platform state (Postgres 16, Redis 7).
- `aether-traefik` — ingress; dynamic config + ACME live in the shared volume `aether-traefik`.
- App deployments: containers named `aether-<depID8>-<number>` on the ingress network with alias `app-<appID8>`; the old container is removed when a new deploy succeeds (frees the public port).

## Ingress / domains / TLS

- Domains: `api/internal/modules/domains/` (application + provision + worker). Free domains under `AETHER_FREE_DOMAIN_BASE` (`apps.aether.local`), custom domains with ACME (`AETHER_CERT_EMAIL`, `AETHER_ACME_DIR`), and the Traefik dynamic config is written into the shared volume.
- If a domain provision/TLS change behaves oddly, check the traefik logs and the shared volume contents before touching code.

## Operational safety (AGENTS.md — hard rules)

1. **NEVER drop/truncate/delete real production data.** DB writes only with explicit authorization.
2. **Never mass-remove containers**: no `podman rm -f $(podman ps -aq)` and no `--filter name=aether-` (catches infra). Operate by exact container name only.
3. Do not stop the test containers (`aether-test-pg`, `aether-redis-test`) — the test suite depends on them.
4. Podman machine has 4GB — watch for OOM on heavy builds; avoid parallel heavy builds.

## Troubleshooting recipes

- API unhealthy: `podman logs aether-api` → check DB reachability and migrations.
- Deploy fails: read the deployment log under `~/.aether/logs/deployments/<depID>.log` (also visible in the UI) and `podman logs <app container>`.
- Port conflicts on host dev: API dev uses :8090 by design (container owns :8080).
- Image build fails in the worker: confirm pack exists in the image (`podman run --rm aether.local/api:1 -- pack --version`); check the deployment log "cnb:" lines for detection; if "No buildpack groups passed detection" the app falls back to the generated Dockerfile.
- Registry local `aether-registry:5000` (HTTP) — os pulls do pack passam pelo podman do host; `~/.config/containers/registries.conf` precisa do `[[registry]] localhost:5000 insecure=true`.

## Verifying platform changes

- `./install.sh start` must end with "Aether is running." and `/api/v1/ready` returning 200.
- Container topology intact: `podman ps` shows aether-api, aether-postgres, aether-redis, aether-traefik.
- Keep `AGENTS.md` updated if operational rules change.
